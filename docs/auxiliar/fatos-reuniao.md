# Mapeamento Técnico de Requisitos e Decisões — Sistema de Webhooks

Este documento serve como a fonte única de verdade (Single Source of Truth) contendo o mapeamento exaustivo de todas as discussões técnicas, decisões, descartes, adiamentos e questões em aberto extraídos diretamente da transcrição da reunião técnica (`TRANSCRICAO.md`).

## Tabela de Classificação e Mapeamento

| Classificação Obrigatória | Assunto/Item | Motivo / Trade-off | Referências ao Sistema | Citação Exata |
| :--- | :--- | :--- | :--- | :--- |
| **[DECIDIDO]** | Sentido do fluxo de webhooks exclusivamente de saída (*outbound*) | Os clientes querem apenas receber notificações sobre as mudanças de status dos seus pedidos, não havendo necessidade de fluxo de entrada (*inbound*). Isso simplifica a arquitetura e os requisitos de segurança do módulo. | | `[09:02] Sofia` e `[09:02] Marcos` |
| **[DECIDIDO]** | Adoção do padrão *Transactional Outbox* no MySQL existente em vez de envio síncrono ou serviço de filas externo | Evita lentidão na transação de mudança de status (que já executa operações pesadas como atualizar `orders`, inserir em `order_status_history` e decrementar `stock_quantity`). Garante atomicidade: se a transação falhar, o evento não é gerado; se for concluída, o evento é gravado. Evita o custo operacional e complexidade de subir nova infraestrutura (como Redis Cluster). | `src/modules/orders`, MySQL, `orders`, `order_status_history`, `stock_quantity`, Prisma | `[09:04] Bruno`, `[09:06] Diego` e `[09:07] Diego` |
| **[DESCARTADO]** | Uso de Redis Cluster ou Redis Streams para gerenciar a fila de eventos de webhook | Considerado *overengineering* para o tamanho atual da equipe de desenvolvimento (time pequeno). A tabela transactional outbox no MySQL atende ao requisito com menor custo de infraestrutura e gerenciamento. | MySQL | `[09:07] Diego` e `[09:07] Larissa` |
| **[DECIDIDO]** | Mecanismo de leitura da tabela de outbox via *polling* em loop a cada 2 segundos | O worker lerá os eventos pendentes mais antigos em pequenos lotes (*batches*), processando-os e alterando seu status. O tempo de resposta de 2 segundos atende com ampla folga o requisito de entrega em "tempo real" (abaixo de 10 segundos) estipulado pelos clientes. | | `[09:09] Diego`, `[09:10] Larissa` e `[09:10] Marcos` |
| **[DESCARTADO]** | Uso de *Triggers* de Banco de Dados para notificação reativa do Worker | O MySQL não possui mecanismos nativos de *listener* (como o `NOTIFY/LISTEN` do Postgres). Triggers no MySQL só executam instruções SQL e não notificam sistemas externos de forma limpa, exigindo improvisações propensas a falhas (ex: escrita em arquivos ou requisições HTTP). | MySQL | `[09:09] Diego` |
| **[DECIDIDO]** | Criação de índices específicos nas colunas de status e data de criação (`created_at`) da outbox | Otimiza o desempenho das consultas executadas pelo worker. Permite buscar rapidamente apenas registros pendentes em lotes pequenos, evitando lentidões na base à medida que o volume de registros acumulados aumenta. | Tabela de outbox, `created_at` | `[09:08] Diego` |
| **[ADIADO]** | Arquivamento automático de linhas entregues na outbox após 30 dias | Embora importante para evitar o crescimento excessivo e degradação de performance da tabela de outbox, o processo de arquivamento dos registros antigos de entrega foi classificado como fora do escopo desta entrega inicial. | Tabela de outbox | `[09:08] Diego` |
| **[DECIDIDO]** | Worker executando como um processo Node.js independente da API principal | Garante robustez ao fluxo de entrega dos webhooks. Se a API precisar ser reiniciada, o worker continua em execução separada. Compartilha a mesma stack técnica e conexão com o banco de dados, porém em um ciclo de vida isolado. | `src/server.ts`, `src/worker.ts`, script `npm run worker`, Prisma client | `[09:11] Diego`, `[09:11] Larissa` e `[09:11] Bruno` |
| **[DECIDIDO]** | Garantia de ordenação de eventos por pedido usando *single-worker* com ordenação implícita | Com apenas uma instância ativa do worker executando sequencialmente por ordem de `created_at` da outbox, garante-se que o cliente receba os eventos do mesmo pedido na ordem correta, sem necessidade de complexidades de ordenação global nesta fase. | `order_id`, `created_at` | `[09:12] Diego` e `[09:13] Larissa` |
| **[ADIADO]** | Escalabilidade para múltiplos workers paralelos com ordenação por partição ou *lock* pessimista | Mapeado como uma necessidade futura de escalabilidade caso o fluxo de envio aumente. O design correspondente foi postergado, pois o *single-worker* é considerado suficiente para o escopo atual de lançamento. | | `[09:13] Diego` |
| **[DECIDIDO]** | Política de retentativas com 5 tentativas e *backoff* exponencial (1m, 5m, 30m, 2h, 12h) | Cobre uma janela de contingência de aproximadamente 15 horas entre a primeira falha e o descarte definitivo. Esse intervalo é suficiente para mitigar indisponibilidades prolongadas no servidor do cliente (como manutenções programadas de até 2 horas). Evita as desvantagens de retries infinitos (gargalos no worker) e 3 retries (tempo de tolerância curto de apenas 30 min). | | `[09:15] Diego`, `[09:16] Diego` e `[09:17] Diego` |
| **[DECIDIDO]** | Gravação de falhas definitivas de envio em uma tabela de Dead Letter Queue (DLQ) separada | Os dados dos eventos que esgotaram todas as 5 tentativas de envio serão movidos para uma tabela `webhook_dead_letter` com o payload original, o motivo detalhado da falha e o timestamp. Isso mantém a tabela de outbox limpa e otimizada, provendo um histórico para debug e suporte. | | `[09:18] Diego` |
| **[DECIDIDO]** | Endpoint para reprocessamento manual de eventos da DLQ por administradores | Disponibilização de uma rota administrativa (`POST /admin/webhooks/dead-letter/:id/replay`) para recuperar um evento que falhou de forma definitiva e reinseri-lo na outbox principal como pendente. | | `[09:18] Diego` |
| **[DECIDIDO]** | Validação de requisições via assinatura criptográfica HMAC-SHA256 | Segurança. Cada requisição enviará o hash do payload gerado com uma chave compartilhada e algoritmo SHA-256 no header `X-Signature`. Isso permite que os servidores dos clientes validem que a mensagem foi gerada genuinamente por nós e que os dados não sofreram adulteração no trajeto. É o padrão aceito pelo mercado. | Header `X-Signature` | `[09:20] Sofia` e `[09:20] Bruno` |
| **[DECIDIDO]** | Chave secreta (*secret*) única por endpoint de webhook cadastrado | Princípio do menor privilégio. Se um cliente vazar as chaves de um dos seus ambientes ou sistemas integrados, apenas aquele endpoint de webhook específico é comprometido, ao invés de expor a segurança de todas as suas integrações na plataforma. | | `[09:21] Sofia` e `[09:21] Bruno` |
| **[DECIDIDO]** | Rotação de chaves (*secrets*) com período de transição (*grace period*) de 24 horas | Permite ao cliente renovar sua chave de segurança via API. Durante o processo, a chave antiga permanecerá válida para verificação por 24 horas. Isso dá margem para que os sistemas do cliente façam a atualização da secret internamente sem risco de rejeição ou perda de notificações. | | `[09:21] Sofia` |
| **[DECIDIDO]** | Obrigatoriedade de HTTPS (TLS) para as URLs configuradas para os webhooks | Proteção dos dados sigilosos dos pedidos em trânsito. URLs contendo protocolo HTTP convencional serão recusadas na camada de entrada e validação. | Validação do schema Zod | `[09:23] Sofia` |
| **[DECIDIDO]** | Limite rígido de tamanho do payload do webhook a 64KB com falha de validação | Previne abuso de consumo de memória e latência de rede. payloads que ultrapassarem 64KB não serão enviados e dispararão um erro explícito de validação (rejeitou-se truncar os dados, pois payloads desse porte indicam anomalias). Para evitar exceder o limite, o payload carregará dados de forma enxuta. | | `[09:23] Sofia`, `[09:24] Diego` e `[09:24] Larissa` |
| **[DECIDIDO]** | Garantia de entrega *At-Least-Once* com cabeçalho de deduplicação `X-Event-Id` no cliente | Evita a complexidade excessiva exigida para implementar entrega *Exactly-Once* (que demandaria coordenação bilateral complexa). Manda um UUID de identificação exclusivo do evento no header `X-Event-Id` para que os sistemas do cliente façam a deduplicação de mensagens duplicadas. É o padrão de mercado (usado por Stripe e GitHub). | Header `X-Event-Id` | `[09:24] Diego`, `[09:25] Diego` e `[09:25] Sofia` |
| **[DECIDIDO]** | Criação do módulo sob a estrutura de arquivos e padrões de design existentes do projeto | Preservação da arquitetura e legibilidade da codebase. O módulo será criado em `src/modules/webhooks` composto de controller, service, repository, routes e schemas Zod. Códigos de erro utilizarão o prefixo `WEBHOOK_` e estenderão a classe `AppError`. Reúsa-se o logger (Pino), o pool do Prisma e o middleware de erros centralizado. | `src/modules`, `AppError`, Logger (`Pino`), middleware de erros centralizado, Prisma Client, Zod schemas | `[09:27] Bruno`, `[09:28] Bruno`, `[09:28] Diego` e `[09:30] Larissa` |
| **[DECIDIDO]** | Instanciação de cliente separado do Prisma (`PrismaClient`) para o processo do Worker | Sendo o worker executado em um processo Node.js isolado da API principal, ele deve instanciar seu próprio cliente de banco de dados, compartilhando o pool e a variável `DATABASE_URL` comum. | PrismaClient, `DATABASE_URL` | `[09:29] Diego` e `[09:30] Bruno` |
